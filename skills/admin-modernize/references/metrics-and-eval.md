# 指标、基准评测与治理

## 四项指标（D1 里定现值和目标值）

| 指标 | 定义 | 怎么量 |
|---|---|---|
| 每页人工返工时长 | AI 初稿到可合并之间，人工修改花的时间 | PR 里「AI 初稿提交」到合并之间的人工提交数和耗时；拿不到就让经手人自报 |
| 首次检查通过率 | AI 第一次交付时，仓库的检查命令一次通过的比例 | 基准评测里记录 |
| 接后端耗时 | 原型就绪到真实数据在测试环境显示正确 | 从原型 PR 合并到联调完成的日历时间，另记工作量 |
| 契约不一致数 | 切到真接口时，开发态响应校验报出的字段、类型、枚举差异 | 校验日志计数 |

辅助：存量基线总量及月降幅；新增违规数（应为 0）。

## 基准需求集

留 3–5 条来自真实需求的页面规格（脱敏），覆盖：列表加抽屉、列表加弹窗、详情、表单、主从表。每条包含：

- 需求文本，和一份契约（类型或 OpenAPI 片段）；
- 自动检查：检查命令通过、截图命令无报错；
- 人工检查：截图对照要点（布局、状态、文案）。

放在 `docs/ai-benchmarks/`，随仓库版本管理。

## 评测流程

1. 开一个干净会话：只有仓库和入口文件，不加额外提示。
2. 给一条基准需求，让 AI 按 `new-page` 生成。
3. 记录：首次是否通过检查、人工改动点、耗时。
4. 把人工改动点按原因归类，**改设施，不改那一页**：

| 原因 | 改什么 |
|---|---|
| 违反规范 | 补 lint 规则或样板页 |
| 用错或缺少组件 | 补或改标准件 |
| 请求、分页、枚举处理不对 | 改数据层 |
| 字段对不上 | 改契约流程 |
| 业务理解错 | 改需求模板 |

5. 重跑触发：改规则、改标准件、改入口文件、升级 AI 模型。

评分表（CSV）：`date,benchmark,model,first_pass,rework_minutes,causes,notes`。

## 治理

- 标准 v1 在试点后冻结。变更需写明动机、重跑基准、记变更日志并升版本号。
- 标准件、规则包、入口文件指定负责人（CODEOWNERS），不由各页面作者各改各的。
- 废弃用标记加基线：旧写法标 deprecated，存量计入基线，新增为零。
- 先定高成本项（token、页面骨架、数据层约定），再定可逆项，避免同一项反复改。

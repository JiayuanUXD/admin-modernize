# admin-legacy-migration：存量按价值逐步迁

存量页面的价值是「别带坏 AI」和「用户体验一致」，不是「必须全改完」。新代码立即合规，存量由基线冻结，迁移按价值排，不大爆炸。

## 排优先级

价值 = 访问量 × 改动频率 × 违规密度。访问量向用户要，改动频率和违规密度来自 `admin-recon`。长尾页面不动，列进「不迁清单」并写原因。

## 三个通道

1. **碰到就改**：任何 PR 触及某页，同一个 PR 把它触及的文件迁到新标准，并收紧基线。日常主力。
2. **批量**：对高价值模块，一批一个模块（按复杂度定页数），一个提交。
3. **路由级替换**：旧页面在另一套技术栈或服务端模板里时，新页面用新栈，两者通过共享外壳或微前端并存，逐页替换。不在同一个页面里混用两套。

## 方案必含

交迁移方案时，下面七项缺一项不算完整方案：

1. 优先级依据：访问量从哪来（向用户要），不迁清单。
2. 批次表：每批的页、违规数、风险；黑盒组件单列。
3. 与在做需求、近 90 天热点的错开；无法判断的列入待确认。
4. 并行与否：默认串行，由用户定。
5. 基线：每批收紧基线的命令与预期降幅；还没有基线就先说明用哪套规则建。
6. 验证：每页的验证方式，和未验证页清单。
7. 阻塞项：缺哪些物料（统一浮层组件、token 表、检查脚本）。物料不在就停下问，不自造标准。

## 批次流程

1. 选批并告知团队，避开近 90 天改动集中的模块，或与在做的需求错开。
2. 用 `admin-preview-loop` 对批内页面截「迁移前」图。
3. 只做结构和视觉迁移，不改业务逻辑。
4. 跑检查命令。
5. 截「迁移后」图比对，每处差异判断是预期还是回归。
6. 收紧基线：`node <插件根>/skills/admin-guardrails/scripts/ratchet.mjs --config <配置> --update-baseline`。
7. 一批一个提交。PR 说明必含四块：迁了哪些页、未验证的页及原因、发现但没修的问题、基线变化。

用户说「不用截图」时照做，但同时给出替代做法：改前后的渲染快照或 DOM 比对、逐页人工点验清单，并建议风险最高的 1–2 页仍补图，由用户决定。PR 里逐页写「未验证」，不能写成「无回归」。

## 视觉与逻辑分开

迁移期间发现 bug，记下来另开提交。视觉迁移的提交里混了逻辑改动，回归时无法判断是哪个引起的。

## 黑盒组件

复杂交互（表达式编辑器、拖拽、大型可编辑表格、富文本）不改内部。外面包一层标准容器，加快照或冒烟，单独排期。

## 机械替换用脚本

成片的机械改写（色值映射到 token、组件换名）用 codemod 或 AST 工具，不要靠 AI 逐文件手改。流程：脚本改、抽样复核、跑检查、截图比对。AI 适合写这个脚本。

## 并行

批内文件互不相交时可以并行，每批一个独立分支或工作树，是否并行由用户定。标准件和基线文件的改动串行合并，基线冲突时合并后重跑 `--update-baseline`。

## 结束条件

基线已经很低，剩下的页面几乎没人访问：停下，写下「不迁清单」。

## 常见错误

- 一次迁整个系统。
- 迁移时顺手改逻辑。
- 没有迁移前截图，回归无从比对。
- 迁完不收紧基线，给回退留了余地。
- 脚本批量替换后没有抽样复核。
